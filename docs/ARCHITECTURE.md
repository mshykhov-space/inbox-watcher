# Архитектура inbox-watcher

Сервис мониторит Gmail-инбокс, классифицирует входящие письма через выбранный LLM (облачный или локальный, с fallback) и шлёт push-уведомления о важных в Telegram с deep-link на письмо.
Требование №1 - zero-miss: пропущенное личное письмо или письмо рекрутёра хуже любого дубля или ложного срабатывания.

## Архитектурное решение: polling, не push

Gmail опрашивается раз в `POLL_INTERVAL_SECONDS` (дефолт 60с). Вариант с Pub/Sub push
(`users.watch()` + webhook) рассмотрен и отклонён: выигрыш в задержке (секунды vs минута)
кейсу ничего не даёт, а цена - GCP topic/подписка/IAM, публичный endpoint, JWT-верификация,
курсор historyId и watch с молчаливым протуханием за 7 дней - пять лишних точек отказа.
Квоты позволяют опрашивать хоть каждые 30с: 1M units/день, `messages.list` = 5 units
(при 30с это 1.4% квоты). Простота = надёжность.

## Компоненты

| Компонент | Ответственность |
|-----------|-----------------|
| Ingest | Polling `messages.list` (query `newer_than:1d -in:draft -from:me`) раз в `POLL_INTERVAL_SECONDS`, OAuth refresh token. Своя почта отсекается на стороне Gmail: каждый автосейв черновика получает новый message id (дедуп бессилен), а тело драфта/реплая цитирует входящее - без фильтра классификатор принимает его за новое письмо рекрутёра |
| Classifier | Настраиваемая через `AI_PROVIDERS` последовательность Gemini, Anthropic и OpenAI-совместимых API. Модель, URL, JSON-режим и необязательный `thinking.type` для совместимых API задаются отдельно для каждого провайдера; старые env-флаги работают без явного списка. Конфигурация проверяется при старте, пустая цепочка отклоняется. Первый успешный ответ побеждает; все упали -> уведомление "unclassified". Справочник: `setup/ai-providers.md`. Оси: importance выводится из category, urgency отмечает ограниченность по времени, action отдельно извлекает конкретный следующий шаг пользователя и остаётся пустым для подтверждений/информационных писем. Application acknowledgement остаётся автоматикой, даже если подписан именем рекрутера. Порядок полей схемы = порядок решения: category первым, action после verdict, reason после action. В input обязателен From. Summary - одно предложение по-русски о факте без повтора action и обещаний процесса. Reason - одно предложение по-английски только для лога решений |
| Notifier | Telegram Bot API. Формат сообщения - канон в `telegram-notifications.md` (типизированный заголовок, опциональное конкретное action, саммари, тело письма свёрнутой цитатой, account-pinned линки). Всё важное шлётся немедленно |
| State | SQLite на `/state`: обработанные message id (дедуп), лог решений классификатора (вердикт, company, action, reason; для unclassified - текст ошибок всей цепочки). Колонка action добавляется существующей базе идемпотентной миграцией. Строки старше 7 дней прунятся ежесуточно |
| HTTP | http4k/Undertow: `/health` - честный liveness poll-цикла; `/metrics` - Prometheus (micrometer): обработанные письма/poll/JVM плюс `classifier_api_requests_total`, `classifier_api_request_duration_seconds`, `classifier_api_tokens_total` с provider/model/status/outcome, без содержимого писем в labels. Скрейпится ServiceMonitor'ом чарта |

## Поток

1. Каждые `POLL_INTERVAL_SECONDS`: `messages.list` (query `newer_than:1d -in:draft -from:me`), отфильтровать уже обработанные по State.
2. `messages.get` для новых -> заголовки + тело.
3. Classifier -> JSON `{category, importance, urgency, action, reason, company, summary}`.
4. Гейт пуша: importance==important или unclassified -> Telegram push. Решение по каждому письму пишется в State ПОСЛЕ успешной доставки (упали до записи -> ретрай следующим poll).

Таксономия категорий: `recruiter-interview-request`, `recruiter-rejection`, `recruiter-generic`, `ai-news`,
`personal`, `transactional`, `other`. Личная переписка с людьми вне поиска работы
(друзья, семья, коллеги, индивидуальные ответы поддержки и сообщения через платформы)
получает `personal` и всегда `important`, даже без просьбы или следующего действия.
Парсер сохраняет этот инвариант при противоречивом `importance` от модели.
Массовые продажи, маркетинг и автоматика с подписью человека остаются `other`.
Urgency определяется ожиданием ответа/сроком, а не самим фактом личного письма.
Новые правила применяются к новым письмам; уже обработанные ID повторно не отправляются.
Дополнительно уведомляем об автоматических письмах двух категорий:
- `ai-news`: официальные анонсы моделей/фич от самих AI-вендоров (From-домен вендора: OpenAI, Anthropic,
  Google/DeepMind), important + not_urgent; сторонние рассылки ПРО AI, маркетинг, devrel-гайды/туториалы
  и billing вендоров - `other`.
- `transactional`: автоматика по СОБСТВЕННЫМ действиям юзера - бронь/заказ/билет/платёж/подписка
  подтверждена, доставлена, отменена, не прошла. Два условия сразу: действие инициировал юзер И письмо
  сообщает смену состояния его денег/заказа/аккаунта. Important; отмена/фейл платежа = urgent. Маркетинг,
  рекомендации, «тебе теперь доступно X» (eligibility/фичи), sync-подтверждения планировщиков
  («бронь добавлена в план поездки») и промежуточные статусы доставки («собран», «передан перевозчику» -
  пуш-ценность только у концов: подтверждён/доставлен/проблема) тех же сервисов - `other`.
  Смена условий/тарифов сервиса «проверьте свои позиции» - `other` + not_important.

## Deep-link на письмо

- Основной: `https://mail.google.com/mail/?authuser=<email>#all/<threadId>` - Gmail роутит треды, id реплая ведёт мимо. Аккаунт пинится ТОЛЬКО через `?authuser=`: email в слоте `/u/` рисует "Temporary Error".
- Fallback "Похожие": `#search/from:<адрес отправителя>` - на телефоне прямой линк открывает голый инбокс (мобильный веб-Gmail теряет `#`-фрагмент), по отправителю письмо находится руками.
- В приложение Gmail: линк "Приложение" -> публичная страница `/open/{threadId}` этого же сервиса (`PUBLIC_BASE_URL`, наружу через Cloudflare tunnel, публичен только путь `/open`). Страница прыгает в недокументированную схему `googlegmail:///cv={threadId}` с fallback на веб. Напрямую из Telegram так нельзя: Bot API пропускает только http/https/tg, а universal links для mail.google.com сломаны на стороне Google (AASA редиректит на www.google.com, где 404).
- Мобильный Telegram открывает http-линки во встроенном браузере, который теряет `#`-фрагмент - прямой веб-линк на телефоне открывает голый инбокс. Поэтому саммари в уведомлении - основной канал, ссылки = удобство.

## Инварианты надёжности ("Грабли")

1. OAuth consent screen обязан быть в статусе "In production" - в "Testing" refresh token умирает за 7 дней.
2. Канарейка тишины (`SilenceCanary`, env `SILENCE_ALERT_HOURS`, дефолт 12ч): ни одного нового письма
   дольше порога -> Telegram-алерт раз в период. Ловит то, что fail-loud не видит: всё «работает», но
   ничего не приходит (умерший OAuth-грант, отозванный scope). Точка отсчёта - `max(processed_at)`
   из State (переживает рестарты), на пустой базе - старт сервиса.
3. Сбой классификации -> уведомление "unclassified" вместо тишины.
4. `/health` = живость poll-цикла: мёртвый/зависший поток планировщика не даёт ошибок, единственный
   симптом - poll'ы перестали завершаться; 503 -> k8s рестарт.
5. First-run seeding: первый poll на пустой базе помечает весь `newer_than`-бэклог обработанным
   без классификации и пуша (reason `first-run seed`) + один алерт с количеством - иначе свежий PVC
   флудит сутками старых уведомлений. Срабатывает раз на процесс.
6. `EmailProcessor` проверяет дедуп до загрузки письма и пишет решение после требуемой доставки.
   Ошибка обработки оставляет id для следующего poll и вызывает error callback с Telegram-алертом.
   Исходящий HTTP-клиент ограничивает connect 10 секундами, запрос 30 секундами;
   отдельного retry-цикла внутри клиентов нет, классификаторы используют последовательный fallback.
   `TelegramAlerter` работает best-effort: транспортную ошибку логирует, но не выбрасывает наружу.

## Эволюция

- Сейчас: polling-пайплайн, отлажен на живом инбоксе.
- Дальше (опционально): human-in-the-loop - кнопки подтверждения в Telegram копят размеченный сет для few-shot/тюнинга промпта и поведенческих сигналов по отправителям.
